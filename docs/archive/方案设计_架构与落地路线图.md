## 一、核心设计原则

1. **彻底解耦**：三大模块（客服、选品、推广）互不直接调用，通过数据库/消息队列通信。任一模块挂掉不阻断其余模块。
2. **失效即降级，而非中断**：每个模块有健康探针，连续失败自动从 `AUTO` 切到 `MANUAL`，未完成动作进人工工单队列，**数据不丢**。
3. **人工可随时介入，修复后一键回切**：MANUAL 状态下人工在后台处理工单；修复接口后手动/自动恢复 `AUTO`。
4. **关键动作默认人工确认**：发货（实物）、公开发帖等高风险/不可逆动作，默认走"AI 生成草稿 → 人工一键确认"，降低封号与误操作风险。
5. **风险隔离**：每个平台账号独立设备指纹 + IP，单账号低频，模拟真人作息。

## 二、解耦架构总览

```
┌──────────────────────────────────────────────────────────────┐
│                     编排层 Orchestrator                        │
│   任务调度(cron) + 模块状态机 + 健康监控 + 人工工单中心        │
└──────────────────────────────────────────────────────────────┘
        │                    │                     │
        │  (异步/DB/MQ 解耦)  │                     │
   ┌────▼─────────┐    ┌─────▼────────┐     ┌──────▼─────────┐
   │  客服模块     │    │  选品模块     │     │  推广模块       │
   │  Customer    │    │  Sourcing    │     │  Promotion      │
   │  状态:AUTO   │    │  状态:AUTO   │     │  状态:AUTO      │
   ├──────────────┤    ├──────────────┤     ├────────────────┤
   │闲鱼私信接入   │    │1688/PDD选品  │     │小红书/抖音发帖  │
   │LLM拟人回复    │    │爆品打分      │     │LLM文案+模板配图 │
   │议价/自动发货  │    │选品清单      │     │定时发布         │
   └──────┬───────┘    └──────┬───────┘     └───────┬────────┘
          │                   │                     │
   ┌──────▼───────────────────▼─────────────────────▼────────┐
   │              共享数据层 (PostgreSQL/MySQL + Redis)        │
   │  商品库 / 订单 / 会话 / 选品清单 / 帖文库 / 工单 / 状态   │
   └──────────────────────────────────────────────────────────┘
                              │
                   ┌──────────▼──────────┐
                   │   人工后台 Web 控制台 │
                   │  工单处理/状态切换/审批 │
                   └─────────────────────┘
```

**为什么这样能做到"单点失效不阻断"**：三个模块各自是独立进程/服务，只通过共享数据层和工单队列通信，没有同步调用链。发帖模块整个挂掉，客服和选品照常自动运行；发帖的待发内容进工单队列等人工。

## 三、模块状态机（人工兜底核心机制）

每个模块在编排层维护一个状态，状态流转如下：

```
        ┌─────────────────────────────────────────────────┐
        │                                                  │
        ▼                                                  │
   ┌─────────┐  健康探针连续失败N次   ┌──────────┐        │
   │  AUTO   │ ─────────────────────► │  MANUAL  │        │
   │ 全自动   │                        │ 人工接管  │        │
   └─────────┘ ◄───────────────────── └──────────┘        │
        ▲      探针恢复+人工确认/自动      │                │
        │                                 │ 生成工单        │
        │                          ┌──────▼──────┐         │
        └──────────────────────────│  工单队列    │─────────┘
            人工处理完成回写         │ (动作不丢)   │
                                   └─────────────┘
```

| 状态 | 行为 | 进入条件 | 退出条件 |
|---|---|---|---|
| `AUTO` | 全自动执行 | 健康探针正常 | 探针连续失败 N 次 → MANUAL |
| `MANUAL` | 自动暂停，新任务转工单，推送告警给运营 | 接口失效/封号/异常率超阈值 | 探针恢复 + 人工点"恢复" → AUTO |
| `工单队列` | 降级期间未完成动作（待发货、待回复、待发帖）入队，人工后台逐条处理 | — | 人工处理完标记完成 |

**健康探针示例**：
- 客服模块：定时发一条测试 WebSocket 心跳/拉取会话列表，失败 = 协议可能失效
- 选品模块：定时调一次 Onebound 接口，返回异常/限流 = 降级
- 推广模块：定时检测发布登录态 cookie 是否有效，失效 = 降级到人工发

**告警通道**：降级时通过飞书/钉钉/企微机器人推送，让运营第一时间知道"哪个模块掉了、有多少工单待处理"。

## 四、模块选型建议（A 的结论并入）

### 4.1 客服模块（风险最高，需 Demo 实测）
- **首选**：`XianyuAutoAgent`（约 8000 星，GPL-3.0，Python）做基座，二开。
  - 优点：专家分诊 + 阶梯议价已内置，社区活跃
  - 改造点：① LLM 接口换成通义千问/Claude；② 接入自有 RAG 知识库（商品 FAQ/退换货）；③ 加状态机探针和工单上报
- **备选**：`xianyu-auto-reply`（FastAPI 全栈，含自动发货/库存，AGPL-3.0）——功能更全但 AGPL 限制商用闭源
- **底层依赖**：`cv-cat/XianYuApis`（逆向 WebSocket 私信协议）——**这是最大变量，C 阶段优先验证**
- **发货策略**：虚拟商品自动发；实物商品 AI 识别"已付款待发货"→ 生成工单 → 人工确认下单 1688/PDD（实物端到端自动采购目前无成熟方案）

### 4.2 选品模块（最稳，优先用付费服务）
- **数据源**：万邦 Onebound API（1688 + 拼多多，按图搜索/搜索词统计/选品中心）+ 可选妙手 ERP
- **爆品打分**：拉销量/价格/评价/搜索热度 → LLM 做"利润测算 + 蓝海判断 + 评分排序" → 输出每日选品清单（人工勾选确认上架）
- 优点：靠服务方维护，不自己扛风控，最适合先跑通

### 4.3 推广模块（封号风险次高）
- **发布**：`social-auto-upload`（8 平台浏览器自动化，patchright 隐身）
- **内容+配图**：参考 `Auto-Redbook-Skills` 思路——LLM 写文案 → Markdown → HTML/CSS 模板 → Playwright 截图成 1080×1440 图片卡片（**不用文生图大模型，更可控**）
- **策略**：默认生成草稿 + 默认私密发布 → 人工复核 → 一键公开；单账号每日限量，养号优先

- [ ] 跑通 Onebound 一个选品接口（确认数据可拉）
- [ ] 跑通 `social-auto-upload` 在小红书发一条私密测试帖
- **产出**：三条"今天能否接通"的实测结论；任一不通则调整方案形态

### Phase 1 · 单模块自动化 + 人工兜底骨架（2-3 周）
- [ ] 搭编排层 + 数据层 + 状态机 + 工单后台（先做骨架，三模块共用）
- [ ] 客服模块接 XianyuAutoAgent + 通义千问 + RAG，跑通"收消息→AI 回复→议价"
- [ ] 健康探针 + AUTO/MANUAL 自动切换 + 告警跑通（先在客服模块验证整套兜底机制）

### Phase 2 · 三模块打通成流水线（3-4 周）
- [ ] 选品模块：每日选品清单 → 人工确认 → 闲鱼半自动上架
- [ ] 推广模块：每日选品 → LLM 文案 → 模板配图 → 定时私密发布 → 人工复核公开
- [ ] 三模块全部接入状态机与工单中心

### Phase 3 · 打磨与风控（持续）
- [ ] 养号策略、频控、设备指纹/IP 隔离
- [ ] 逆向协议失效的快速修复流程（监控 + 热更新签名）
- [ ] 数据看板：转化、回复质量、封号率、各模块健康度

## 六、技术栈建议

| 层 | 选型 |
|---|---|
| 编排/调度 | Python（与开源项目同语言，便于二开）+ APScheduler/cron |
| 服务框架 | FastAPI |
| 数据层 | PostgreSQL/MySQL + Redis（队列/缓存/状态）|
| LLM | 通义千问 Qwen（国内合规、与 XianYuAssistant 同栈）/ Claude（质量）|
| RAG | 向量库（如 Milvus/pgvector）+ 商品 FAQ 知识库 |
| 浏览器自动化 | Playwright / patchright（隐身）|
| 人工后台 | 轻量 Web（Vue/React）或先用低代码/管理后台模板 |
| 告警 | 飞书/钉钉/企微机器人 |

## 七、关键风险登记（持续跟踪）

| 风险 | 等级 | 应对 |
|---|---|---|
| 闲鱼 sign 协议更新致私信失效 | 高 | 探针监控 + 快速修复流程 + 降级人工 |
| 小红书/抖音账号封号/限流 | 中-高 | 养号、限频、私密复核、多账号隔离 |
| 拼多多无官方 API，第三方数据波动 | 中 | 多数据源、缓存、异常降级 |
| 实物自动发货无闭环 | 中 | 实物走人工确认采购，不强求全自动 |
| 开源项目许可证（GPL/AGPL/禁商用）| 中 | 法务评估，必要时自研替换核心模块 |
