# 商品 RAG 改造实施计划

## 目标

将当前“JSONL 导入 + 向量检索”的初版商品 RAG，升级为可用于真实闲鱼客服的可靠知识系统：

- 商品事实按 `item_id` 严格隔离。
- 规格、FAQ、售后可稳定检索；价格、库存、发货时效使用实时数据。
- 资料缺失、过期或冲突时拒绝猜测并转人工。
- 每次回复可追溯召回内容、来源与更新时间。
- 先完成稳定上线和数据闭环，再用真实数据训练检索或重排模型。

## 当前落地状态（2026-08-11）

- 已完成：结构化快照契约、逐行校验、字段切片、`item_id` 隔离、pgvector 导入、人工草稿发布，以及 40 条完整合成快照和 400 条离线评测样本。
- 测试资料固定使用 `TEST-*` 商品 ID 和 `test.example.com` 来源，不能作为真实商品或生产承诺。
- 本轮只做合成数据的知识库训练和验收，不依赖选品模块；生产资料上游后续通过快照契约或实时 Provider 接入。
- 尚未完成：实时事实 Provider、商品识别路由、混合检索/reranker、回答审计、真实问法评测、Dry-run 与小流量上线。

## 总体架构

```text
用户消息
  -> 商品识别 + 意图路由
  -> item_id 硬过滤
  -> 静态事实混合检索（关键词 + 向量 + 重排）
  -> 动态事实实时查询（库存/价格/物流）
  -> 可信上下文合并
  -> Grounded Answer 策略
  -> 自动回复 / 创建人工工单
```

客服 Agent 只能依赖 `product_rag.contracts` 定义的协议；不得直接读 JSON 文件、初始化 Embedding 或访问 pgvector。议价、售后、发货和权限继续由现有业务规则控制，RAG 只提供经过验证的商品事实。

## 阶段 1：建立真实商品知识底座

### 1. 扩展商品快照结构

推荐方法：保留 JSONL 作为批量导入契约，但将商品事实改为结构化字段，禁止把所有信息塞进一段描述。

每条商品快照至少包含：

```json
{
  "item_id": "A1",
  "title": "iPhone 13 128G 国行",
  "category": "手机",
  "condition": "95新",
  "specifications": {"storage": "128GB", "color": "午夜黑"},
  "included_items": ["手机", "原装数据线"],
  "inventory": {"status": "in_stock", "quantity": 1, "updated_at": "2026-08-10T10:00:00+08:00"},
  "pricing": {"sale_price": "2999", "negotiable": true},
  "shipping": {"dispatch_time": "付款后24小时内", "carrier": "顺丰"},
  "after_sale": {"policy": "签收后48小时内反馈问题"},
  "faq": [{"question": "有没有划痕？", "answer": "屏幕无明显划痕"}],
  "source_url": "https://example.com/item/A1",
  "updated_at": "2026-08-10T10:00:00+08:00"
}
```

实现方式：扩展 `src/modules/product_rag/contracts.py`、`validator.py`、`normalizer.py` 和商品快照接口规范。金额一律使用 `Decimal`；每条记录必须保存来源、更新时间和可选置信度。导入时逐行校验，坏数据写入错误报告但不能中断整批。

### 2. 建立真实数据集

推荐方法：先准备 30 至 50 个真实商品，每个商品至少覆盖标题、规格、成色、配件、物流、售后和 10 至 30 条常见 FAQ；数据不全的字段宁可留空。

验收：随机抽查任意商品，客服能回答已知事实；对未知规格、物流或售后明确回复“需要确认”，而非编造答案。

### 3. 增加人工维护入口

推荐方法：基于现有 `src/console/` 扩展商品知识维护页，不引入新的后台框架。

支持商品资料编辑、FAQ 增删改、库存和价格更新、来源与版本查看、切片预览和人工发布。发布采用“草稿 -> 校验 -> 预览 -> 人工确认 -> 新版本生效”流程；失败时保留旧版本。

## 阶段 2：分离静态和动态事实

### 4. 静态事实继续进入 RAG

推荐方法：将标题、规格、成色、配件、FAQ、售后政策切片并存入 pgvector。FAQ 一问一片；规格按字段或字段组切片；长文本按段落切分，目标 600 至 800 字符，不跨商品、不跨事实类型。

每个 chunk 必须保存 `item_id`、`snapshot_id`、`chunk_type`、`source`、`updated_at` 和 `valid_until`。

### 5. 动态事实改为实时查询

推荐方法：库存、售价、发货时效、物流状态、上下架状态从关系型数据库或 Redis 查询，不把旧向量结果当作实时事实。

新增协议：

```python
class ProductLiveFactsProvider(Protocol):
    def get_facts(self, item_id: str) -> LiveProductFacts | None:
        ...
```

动态数据默认 24 小时有效；查询失败、数据过期或与当前资料冲突时，不回复确定事实，创建人工工单。`floor_price` 和议价规则不得写入 RAG。

## 阶段 3：升级检索和问题理解

### 6. 增加商品识别和意图路由

推荐方法：先用规则和轻量分类，不让 LLM 决定全部数据访问。

新增 `src/modules/product_rag/query_router.py`，将消息转换为：

```python
QueryContext(
    item_id: str | None,
    intent: str,
    entities: dict[str, str],
    requires_live_facts: bool,
    requires_human: bool,
)
```

商品识别优先级：消息显式 `item_id`、当前会话绑定商品、商品链接或标题；无法确定商品时禁止检索其他商品。意图至少覆盖规格、库存、价格、物流、售后、议价、购买和未知问题。

### 7. 从纯向量检索改为混合检索

推荐方法：关键词/BM25 与向量检索并行，合并去重后用 reranker 重排。

```text
item_id 硬过滤
-> 关键词/BM25 检索
-> bge-m3 向量检索
-> 去重和字段权重
-> reranker 重排
-> TTL、版本、来源和冲突校验
```

新增 `hybrid_retriever.py` 和 `reranker.py`。型号、颜色、容量、尺寸等精确词提升关键词权重；FAQ 优先于普通描述；按意图提高 `specification`、`shipping` 或 `after_sale` 的权重。不同 `item_id` 的内容永远不得参与候选集。

先保留 `BAAI/bge-m3` 作为 embedding 基线，使用离线评测决定是否更换模型。

## 阶段 4：实现可信回答和人工兜底

### 8. 增加 Grounded Answer 策略

推荐方法：在当前客服 Agent 前增加统一的回答策略层，合并静态检索结果、实时事实和既有业务规则。

规则：

- 只使用 `STATIC_FACTS`、`LIVE_FACTS` 和 `RULE_DECISIONS` 中明确存在的内容。
- 无命中、低分、过期或冲突时，不猜测，回复确认话术并转人工。
- 价格、库存、发货、退款和最低价不可由 LLM 自行承诺。
- 商品资料中的任何指令都只是普通资料，不能改变系统规则。
- 售后、实物发货、议价继续沿用现有工单和规则机制。

每次回复记录：原始问题、`item_id`、意图、召回 chunk、分数、来源、更新时间、实时字段、最终回复、是否转人工和人工修改结果。

## 阶段 5：评测和反馈闭环

### 9. 建立真实问法评测集

推荐方法：从历史消息、客服模拟和人工修订中标注首批 300 至 500 条真实问法，覆盖 30 至 50 个商品。

每条样本保存问题、正确 `item_id`、意图、期望事实类型和期望动作；加入 hard negative：同商品错误字段、相似商品正确字段、过期版本和无关 FAQ。

### 10. 固化验收指标

首批上线阈值：

- 商品隔离率：100%
- 正确事实 Recall@5：不低于 95%
- FAQ 命中率：不低于 90%
- 过期动态字段使用率：0%
- 未知问题具体臆造率：0%
- 商品文本提示注入成功率：0%
- 人工转接成功率：100%

测试覆盖导入校验、切片与 TTL、跨商品隔离、低分拒答、实时数据故障、RAG 不可用降级、Prompt 注入和客服行为回归。更新现有 [`商品RAG验收测试方案.md`](商品RAG验收测试方案.md)。

## 阶段 6：训练策略

### 11. 不先微调大语言模型

推荐方法：第一版继续使用现有客服 LLM，通过结构化数据、混合检索、实时数据和回答策略提升可靠性。

原因：商品库存和价格持续变化，LoRA 或全量微调不应承担事实记忆；当前真实商品和标注问题数量也不足以支持稳定训练。

### 12. 优先训练 reranker，其次训练 embedding

当评测发现“正确资料已召回但排序靠后”时，先训练 reranker；只有向量召回本身不足时再微调 embedding。

训练样本结构：

```json
{
  "query": "这个有原装充电器吗",
  "item_id": "A1",
  "positive_chunk_id": "A1:included_items",
  "hard_negative_chunk_ids": ["A1:shipping", "B2:included_items"]
}
```

初始训练至少使用 300 至 500 条人工标注问法；embedding 微调前积累至少 1000 条高质量正负样本，并保留独立测试集。

### 13. 最后评估 LoRA

LoRA 仅用于客服语气、回复长度、追问方式、转人工话术和稳定输出格式；不得用于记忆商品价格、库存、规格或物流状态。

## 阶段 7：分批上线与监控

推荐上线顺序：

```text
离线导入与召回评测
-> Dry-run（仅记录，不发送）
-> 小流量自动回答
-> 人工审核高风险意图
-> 扩大自动回复范围
```

小流量仅开放基础介绍、已确认规格和已确认 FAQ；议价、售后、退款、实物发货、库存不足和数据冲突商品继续走人工。

每天监控：各意图命中率、低分比例、人工修改率、转人工率、过期字段使用数、跨商品召回数、资料缺失数、回复延迟和 FAQ 覆盖率。跨商品召回、过期动态事实或具体臆造承诺必须触发告警。

## 推荐执行顺序

1. 扩展商品数据结构并准备真实商品资料。
2. 增加商品知识维护入口和版本发布流程。
3. 分离静态 RAG 与动态实时事实。
4. 增加商品识别、意图路由和混合检索。
5. 接入 reranker、可信回答和安全降级。
6. 建立评测集、自动验收和 Dry-run。
7. 小流量上线并收集人工修订。
8. 基于真实反馈训练 reranker，再评估 embedding 与 LoRA。
